# Modular foundation roadmap

AllMyStuff should provide reusable application capabilities on top of MyOwnMesh: fleet forming and claiming, resource sharing, and optional media and host services. The next work separates those capabilities using the existing mesh integration. **Internal feature separation does not wait for MyOwnMesh v1.0.0. Replacing the mesh integration does require a reviewed upstream contract.**

This roadmap starts from release 0.2.121, commit `b15aa1a277894999a8f01134843c06e892de084b`, reviewed on 2026-09-13. It distinguishes implemented behavior, selected initial work, and proposed profiles. It does not declare new Cargo features, supported platforms, a finalized v1 API, or completion of the work below. The source-cited [responsibility review](reviews/modular-foundation/responsibility-mesh-review.md), [dependency review](reviews/modular-foundation/modularity-dependency-review.md), [platform review](reviews/modular-foundation/headless-platform-review.md), and [behavior review](reviews/modular-foundation/behavior-test-review.md) retain the detailed evidence and limitations. The platform review is the support-matrix reference.

**Stage-one verification.** At integrated commit `152c933920d788b80e5b8c80a580d600ed07e01c`, focused capability and CLI tests passed on Windows x64 with Rust 1.97.1 for defaults disabled, `audio-io` alone, and default host. The [verification ledger](reviews/modular-foundation/stage-one-verification.md) records 38 test executions including ownership and the privileged-offer helper, plus a successful direct-node help process. These results cover the bounded first slices; later profiles and stages remain proposed. Live mesh/media, other platforms, hardware and the declared minimum Rust version remain unqualified.

**Implemented seams.** The desktop GUI drives an `allmystuff-serve` node over local IPC. The node runs application policy/capabilities and consumes a MyOwnMesh daemon through its separate control socket. The root CLI's `serve` command locates and forwards arguments to that node binary. Mobile instead embeds the same daemon and node inside the app and calls node dispatch directly; the mobile-core transport trait does not establish a separate production adapter.

| Boundary | Current ownership | Consequence for modularization |
| --- | --- | --- |
| Root graph, protocol and session crates | AllMyStuff capability/permission model, app wire messages and route state/effects. Protocol also contains the daemon wire mirror and state-path helpers. | Retain the lightweight application model. The measured session dependency tree includes `dirs` platform helpers; do not describe all protocol code as platform-free data. |
| Mesh engine and signaling | MyOwnMesh identity, discovery, connections, channel/track transport and signed network governance. | Adapt the consumer boundary. Do not implement another mesh engine or remove app policy merely because its module is named `mesh`. |
| Claims, fleet UX, shares and consent | AllMyStuff local claim policy, persisted ownership, bootstrap/handoff, resource grants and CEC consent. Signed governance supplies part of the authority these workflows consume. | Retain app decisions and user interaction. Move an individual bootstrap/governance step only when a reviewed replacement preserves credentials, roles, revocation and recovery. |
| Node capability implementations | Capture, encode/decode, audio, input, terminal, clipboard, files/Fleetfiles, storage allocation, drive mounting and site proxying. | Separate these as explicit capabilities, preserving caller authorization as well as implementation. Media transport ownership does not imply media capture/codec ownership. |
| UI, node service and durable app state | AllMyStuff presentation, node lifecycle, OS service integration, app updates, parked networks and application stores. | Keep app lifecycle/state distinct from daemon acquisition and supervision. Sharing `MYOWNMESH_HOME` does not make an app store disposable mesh state. |

The [root workspace](../Cargo.toml) excludes [node](../node/Cargo.toml), [desktop](../gui/src-tauri/Cargo.toml) and [mobile](../gui/mobile/Cargo.toml) workspaces. Root test success does not validate their builds. The GUI is a thin *process client*, but its manifest still depends on the default node; process isolation is not dependency isolation.

The node currently defaults to `host`, which includes `audio-io`, capture, PTY, input and clipboard support. `hwenc` also enables host and FFmpeg. With defaults disabled, several host modules become stubs, but OpenH264/Opus receive codecs, storage, networking, updater and platform services remain. Windows capture also crosses the baseline host gate. This configuration is a capture-less node with remaining native dependencies; **there is no implemented media-free minimal `serve` profile yet**. The existing `UiSink` and separate foreground node already provide a useful starting point without a webview.

**Selected first work.** These are bounded implementation scopes with independent review and validation gates, not completion claims. The initial node lock failure must be resolved with a reviewed dependency diff before its locked graph/build evidence can be collected.

| Lane | Scope | Required evidence before claiming success |
| --- | --- | --- |
| A2: existing host dependency boundary | Make pixels optional under host; gate complete Windows capture; move only verified host-exclusive Windows feature groups under host. Preserve receiver codecs, nonhost LibraryLoader, Fleetfiles Storage/COM, telemetry and service/security APIs. | Selected-package graphs show the intended exclusion; no-default, audio-io and default configurations compile on each claimed target. Default behavior and authorization stay intact. GPU receiver rungs already depend on host, so this cut does not establish an independent hardware-viewer profile. |
| C1: emitted node capabilities | Filter endpoints whose implementation is disabled, at node profile construction rather than changing the bridge's general inventory contract. | Default list unchanged. No-host removes capture sources, control Input Sink and Clipboard Duplex while retaining controller/input sources and viewer sinks. Audio endpoints follow `audio-io`; retaining system audio preserves existing microphone fallback on some platforms, not universal OS-loopback support. |
| C2: inert direct-node help | Recognize first-token `--help`, `-h` and `help` before state, pending updates, logging, sockets or daemon work. | Argument tests and an isolated direct-binary check establish early return; existing version/update/startup/service paths remain intact. The CLI wrapper still applies pending updates before dispatch, so it is outside the inert-help claim. |
| A1: architecture and stages | Record ownership, proposed profiles, support evidence and deletion prerequisites here; link the architecture reference to the committed mesh pin. | Independent documentation review; no runtime or manifest behavior change. |

At the reviewed baseline, direct-node help falls through to startup and is not an inert probe. Only claim the new behavior for a revision that contains and validates the help change. Ordinary foreground startup may initialize stores, attach to a daemon and run update/supervision tasks; a printed startup message is not mesh readiness.

**Proposed profiles.** The labels below describe future consumer choices; they are not implemented feature names or build commands. A consumer should eventually select only its required capabilities while the current full-host default keeps its behavior.

| Proposed choice | Intended inclusion | Evidence still needed |
| --- | --- | --- |
| Minimal serve | Headless app foundation, mesh adapter and authorization for explicitly selected capabilities; no GUI, native capture, audio I/O or codecs. Optional filesystem/proxy/updater/service behavior must be explicit. | Real transitive exclusion, honest capability/command exposure, isolated startup/readiness/shutdown and target qualification. Disabling host today does not meet this definition. |
| Terminal host | Minimal serve plus PTY hosting and its authorized control flow. | Separate PTY from screen/input capture; prove OS prerequisites and real terminal behavior in disposable state. |
| Viewer/controller | App session plus selected receive codecs, rendering/output and control-source behavior, with audio I/O chosen separately. | Separate hardware decode from the current host gate; preserve route identity, grants, buffering and failure behavior. Compiled audio decode alone does not provide playback. |
| Full host | Preserve today's default capability behavior with explicit composition of capture, input, terminal, media and app services. | Default graph/feature parity, real capability coverage and regressions appropriate to each changed plane. |

For every feature cut, check the whole path: dependency/import selection, owned state and startup tasks, advertised endpoints/features, inbound/outbound dispatch, unsupported-operation responses, and teardown. A missing implementation must not remain advertised as usable. Exclusion must be visible in a resolved target graph, not inferred from an optional manifest entry or a lockfile package list. Use selected-package checks: the node workspace can still select its pixels member independently of whether the node needs it.

Authorization and compatibility remain explicit acceptance conditions:

- Keep authenticated sender and arrival-network provenance through claim admission, including device-local public-claim policy and independently established LAN fallback. Preserve pending-claim matching, recorded-owner handoff and rollback when ownership cannot be persisted.
- Keep graph endpoint grants and runtime plane/capability checks before effects reach capture, input, shell, disk or proxies. Session auto-accept is not an authorization decision. Keep directional shares, folder scope, CEC consent/session binding and revocation handling distinct from fleet membership.
- Preserve actual roster behavior during a behavior-preserving cut: the baseline trusts self, recorded owner, local admission records and a daemon-roster cache, retaining its prior cache on failed/empty reads. Presence ownership is not membership authority. Older roster-gossip prose is not the current access-control contract. Freshness/eviction policy changes require a separate reviewed decision.
- Preserve local IPC mechanisms and lifecycle ownership without overstating their assurance: the Windows descriptor is conditional on a supplied service-client SID; Unix mode-setting failure currently warns and continues. No review here proves owner-only access for every deployment. Never widen access as a side effect of modularization.
- Preserve the default CLI/GUI experience, supported peer fallback behavior, pin, and state paths. Do not assume authority to replace another application's running daemon. Avoid implicit service actions or migrations while qualifying a build.

**Platform evidence at the initial review.** "Configured" means repository workflow configuration, not an audited successful workflow or artifact. The detailed [C1 support matrix](reviews/modular-foundation/headless-platform-review.md) distinguishes process paths, architecture-specific limits and actual runs.

| Target family | Configured/intended paths | Qualification at the initial baseline |
| --- | --- | --- |
| Windows x86_64 MSVC | Explicit desktop/CLI/node release target; default-node and root CI. Foreground and SCM paths exist. | Windows root workspace tests passed; node locked dependency resolution failed before compilation. No node/GUI/service runtime proof. A system service still has interactive-session assumptions. |
| Linux x86_64 and aarch64 GNU | Explicit release targets; Linux CI includes a capture-less check after installing the full native development stack. | No Linux build or no-display runtime inspected. Reduced node dependencies and each architecture need separate qualification. |
| macOS x86_64 and aarch64 | Explicit release targets, default-node/root/GUI CI; foreground and launchd paths. | No architecture-specific build/runtime inspected; permissions/frameworks and capture-less builds remain unqualified. |

| Other native targets and browser/Wasm | Future evaluation only; release assets, native dependencies, local IPC and service support constrain the current node. | No support claim. A missing GUI does not by itself prove foreground serve can compile or operate. |

The actual initial Windows evidence is limited: root `cargo test --workspace --locked` succeeded (run `55c240f9-9dd5-4765-a284-9cc5312ad1c5`, 316 unit tests and 3 doc tests); the root session normal/build tree succeeded (`3cf24bf6-4d33-4d00-9bd9-192952aa595c`). The baseline node tree failed at locked resolution (`9eb3cb23-533c-4622-b1bb-73db0f9ed70c`). Later task-branch lock/feature validation is separate evidence and must name its revision, selected lock, target, command and terminal result. A green hardware test that returns early when hardware is absent is not proof that the hardware path ran. Declared Rust 1.88.0 is also not an independently tested minimum; current CI selects moving stable.

After the reviewed eight-package local-version lock correction, node graph run `d618764c-3a72-4607-8c71-3a5a94474828` succeeded on Windows x86_64 with `--locked` (exit 0, 11.088 s); its earlier offline attempt lacked cached `hashlink`, rather than proving a new source mismatch. Manager run `49ab1b24-95bf-42c0-835f-5dcdeb6cbd9a` then succeeded for `cargo check --locked --manifest-path node/Cargo.toml --no-default-features --bin allmystuff-serve` at task commit `3fd1e5ffad5b62ca0c252e1851afff79e105f558` (exit 0, 79.916 s). The selected node lock matches the accepted repair, SHA-256 `81124dd2257d314943037495620808240c98683f9deb43e7b00a67942aa2bd24` using its reviewed LF bytes. This is local Windows compile evidence after lock repair, before the new host/capability/help changes; it proves neither their acceptance nor runtime behavior, other targets, a minimal dependency set or the declared minimum Rust version.

The independently reviewed A2 host correction, commit `cc22ea2a85a3bca6ced82dc8146b77b3cf987c86`, also has targeted Windows graph evidence: `31539d3d-4038-41b7-b01b-3db8199d7aa8` excludes pixels without host, and `9a1e1f50-e291-4672-aae1-7ad687f8fa67` retains default-to-host-to-pixels selection. Comparing `60f585c7-93dd-44f9-9a52-c18e2ed6e34f` with `63930d93-2c44-4412-8b6a-87f2de9a9369` removes the eight moved graphics/input/MediaFoundation groups from the **node's Windows 0.61.3 feature closure**, retaining Storage/COM/Performance/Threading/LibraryLoader. All four runs succeeded. OpenH264, Opus, SQLite and Windows 0.62.2 through other dependencies remain; this is not removal of all Windows graphics across dependency versions or a media-free graph. Final integrated compile/behavior checks remain separate; the [dependency review](reviews/modular-foundation/modularity-dependency-review.md) records the implementation's evidence.

**Later stages and removal gates.** After the initial corrections, separate PTY, audio I/O, receive codecs, capture, storage/proxy and update/service dependencies in bounded slices using the existing adapter. Keep defaults and peer behavior stable; qualify each proposed profile with dependency, compile, capability and isolated runtime evidence. The longer-term goal is a usable headless serve path on targets without the GUI, qualified one target at a time rather than inferred from source portability.

The committed [MyOwnMesh pin](../.myownmesh-rev) is v0.3.21 at this review, with mobile's lock resolving `59143cbdb094b6b99464c224a500e148fd7d2113`. The hand-kept daemon wire mirror and app protocol version are current consumer contracts, not a MyOwnMesh v1.0.0 specification. Before replacing the mesh adapter, settle the supported library/daemon APIs and targets, identity/state continuity, authenticated sender/network metadata, signed governance/MFA/eviction behavior, version/capability negotiation, media framing/backpressure and lifecycle ownership.

| Potential eventual removal | Required replacement and exit evidence |
| --- | --- |
| Hand-kept daemon wire mirror | Reviewed upstream contract with suitable dependency closure, compatibility/error coverage and a supported version policy. Preserve application wire messages separately. |
| Fleet bootstrap/key/admission compatibility | Explicit credential/state migration that preserves consent, identities, roles and revocation, with recovery/rollback and old/new peer evidence. Signed rosters alone are not a replacement for claiming. |
| Old media fallback transports | A declared supported-peer floor plus mixed-version and failure-recovery evidence. Do not remove codecs or fallback paths merely because a newer daemon exists. |
| Daemon bundling, update/restart glue or parked-network emulation | A supported deployment/configuration replacement that preserves disabled settings, service/UI coexistence, state ownership and externally owned daemons. |

Validation commands and reviewed setup recipes live in the linked reports and repository contribution instructions. Important runs belong in the manager's durable run records; this documentation change needs only diff/link/content review. Broad node tests can load default stores through `Mesh::new`, so use reviewed pure filters or a verified disposable profile/testbed. A Windows state-directory override alone does not isolate its fixed node pipe. Live tests require test-owned binaries/state, verified socket isolation and explicit cleanup; a terminal `outcome_unknown` is never permission to replay a command.
